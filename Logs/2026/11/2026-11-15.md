**Prompt:** Do the recommendations from the Astroschedular to Night Planner and remake Lick-2026B-04 plan

**Model:** claude-opus-5-5. **Tokens/CO2:** see `Logs/log_summary.csv` (authoritative).

I took the four "night-planner from AstroScheduler" items from the
Decision Map's Side by side tab and built them into the Lick/Kast path.

**1. Placement by airmass** (`night_planner/retime.py`,
`kast_calculations.retime_schedule`). The greedy tier loop still picks the
targets. A fixed-order dynamic program then re-chooses their starts to
minimise the summed block airmass. It works on a 0.5-min grid and has no
search cap, so it is exact (a test checks it against brute force). I added
insertion on top: each dropped target is tried at every position, best
priority first, and accepted if all placed targets still fit. This is
AstroScheduler's "placed targets may move", without the cap that bit it in
the toy.

The first trial on 2026B-04 exposed a flaw in my own design. Re-timing
moved FRB20240901A to the end of the night for 0.02 in airmass, which
cost a P1 partial (FRB20260310B) that the earliest placement had allowed.
I made partials part of the same search: after full insertions, each
still-dropped target gets the longest partial (by bisection) that fits
when the others shift. The goals now rank as full targets, then partial
minutes, then airmass. With that, the remake keeps both partials and also
gains FRB20260708D as one.

**2. Stability.** `--previous-plan DIR`: 0.002 airmass per minute moved
from that plan's start. A test checks that a run anchored on its own
output reproduces it.

**3. Precedence.** A `schedule_before` target column (targets_io), honoured
by a stable topological order in the re-time step. An infeasible pair
drops the later target with a `schedule_before:` reason, and the partial
backfill checks it too.

**4. Limits as data.** `night_planner/data/site_limits.json` (with the
source of each value) plus `night_planner/site_limits.py`. A run can
override any value with `--limit KEY=VALUE`, which adds optional dec_min
and airmass_max for Lick. `lick_2026b02_calculations.HA_MIN/HA_MAX/DEC_LIMIT`
now come from the file; a test checks the values are unchanged.
`target_window` takes the limits as arguments. The plan's assumptions
record the limits and the placement rule.

**Defaults:** placement is `airmass` by default, and `--placement earliest`
reproduces the old schedule exactly (tested). The limit values are
unchanged. In particular I did **not** adopt AstroScheduler's +72 or 1.7:
those are the author's call.
