## 2026-11-11T07:45Z (approx.) — could calcint be for something else?

**Prompt:** Could the interpolation in calcint.c be for something else, like finding the right parralactic?

**Model:** claude-opus-5-5. **Tokens/CO2:** see `Logs/log_summary.csv` (authoritative).

No. `pa.c` works out the parallactic angle with a formula first, and
`calcint` takes one angle through an exactly linear table. The parallactic
angle depends non-linearly on HA, Dec and latitude, so a one-input linear
table cannot stand in for it, and the comments call the output an
"encoder number". But I flagged a real weakness in the 10-16 check: a
single tub setting cannot separate a 0.87 scale from a constant offset
(PA - 29.05 fits that frame equally well). I proposed testing frames with
widely different TUB values.

## 2026-11-11T08:40Z (approx.) — best-airmass pass, thinking only

**Prompt:** ok, let's think this through, can we always try to observe targets at the best airmass, maybe in the very last step? Don't change code yet, just think it through

**Model:** claude-opus-5-5. **Tokens/CO2:** see `Logs/log_summary.csv` (authoritative).

This was design only. Key observation: a window's close is
min(transit + 3:45, dawn), so earliest-close-first is already transit order
for most targets. The losses are dawn-clipped ties (the rising targets),
left-packed blocks that waste slack, and early setters. Proposal: a stage 2
that keeps the stage-1 set and tiers fixed and only re-times and re-orders.
It would minimise priority-weighted *excess* airmass (over each target's
best tonight) by sliding blocks with a fixed order, then local swaps. It
must re-run the ETC on every move, backfill once, and keep a 15-20 min
safety margin for setting targets. Before building, measure the current
excess airmass on past nights: if it is small, a transit-time tie-break plus
an airmass <= 2.0 cut is enough. The user deferred this.

## 2026-11-11T21:40Z (approx.) — UT block times and a UT axis row

**Prompt:** In the blocked window times, can we add a UT time mode as an option, also add UT time row on the display

**Model:** claude-opus-5-5. **Tokens/CO2:** see `Logs/log_summary.csv` (authoritative).

**Parser.** Every pipeline resolves block and start times through one
function, `scripts/night_plan_io.resolve_local_dt`, so the UT support lives
there. It now accepts `HH:MM UT` (also `UTC` or `Z`, any case, space
optional). The new `resolve_ut_time` places it on the night as the one
instant between local noon on the evening date and local noon the next day
with that UT reading. That handles PST, PDT and HST without per-site rules.
The UT match must come before the existing ISO branch, because `'T' in
'06:30UT'` would otherwise send it there. `--start` gets UT for free.

**Setup page.** A "Times in: local / UT" switch for blocked windows; the
row placeholders follow it, and UT rows are sent with a ` UT` suffix.

**Plan timeline.** A UT axis row between local time and LST, and every hover
box gains a UT line. The new helper is `utClock`: `utHHMM` already existed
with a different meaning, which the syntax check caught. I updated the
`--block` help text in both pipelines.

**Tests:** 8 new in `tests/test_ut_times.py`; the suite is 202 passed,
1 skipped. The server was restarted.

**Found on the way (existing behaviour, not fixed):** on Kast the 5-minute
slew + acquisition before a target can sit inside the end of a blocked
window. Science starts at the block's end, but the move starts 5 minutes
earlier. With a ToO or weather block that time isn't really ours. I
reported it to the user.
